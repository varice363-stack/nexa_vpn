КОНТЕКСТ

======================================================================

Мы приняли фундаментальное решение: Nexa — коммерческая VPN-платформа.
Приложение — лишь один из клиентов. Основной продукт — доступ
(VLESS-конфигурации / ключи). Пользователь может использовать любой
совместимый VPN-клиент.

Новая доменная цепочка:

Account
  ↓
Subscription
  ↓
Provisioning
  ↓
VPN Connection

Arena AI (Flutter/Backend Engineer) провёл анализ текущей кодовой базы
на соответствие этой модели (отчёт прилагается). Изменений в код не
вносилось — это пакет для принятия архитектурных решений.

======================================================================

РЕЗУЛЬТАТЫ АНАЛИЗА (кратко)

======================================================================

1. Текущая модель — «VPN-приложение с серверным каталогом», а не
   «платформа доступа».

2. Provisioning НЕ существует (единственное упоминание — TODO-комментарий
   в backend/src/vpn/vpn.service.ts).

3. Моделей Device и AccessKey нет ни в Prisma, ни в Flutter.

4. ConnectionLog не содержит deviceId — трафик нельзя атрибутировать
   по устройству.

5. Двойной источник истины: role=PREMIUM присваивается вручную И создаётся
   подписка (users.service.ts). При истечении подписки роль не откатывается.

6. Покупка подписки в клиенте — локальная симуляция; backend-эндпоинта
   purchase/webhook нет.

7. Клиент: login UI отсутствует (authProvider готов); QR/импорт/устройства/
   ключи отсутствуют; каркас (domain-интерфейсы + AsyncNotifier + роутер)
   готов к добавлению без перестройки.

8. Backend (NestJS) готов к добавлению Provisioning Module без изменений
   каркаса (паттерн модуля отлажен, глобальные guard'ы, аддитивные
   Prisma-миграции). Оценка: 1–2 дня на модели + CRUD + VLESS URI.

9. Масштабирование: 100–1 000 пользователей — без изменений; 10 000 —
   PgBouncer/Redis/rate-limit; 50 000 — pre-aggregated analytics
   (сейчас GROUP BY по живой таблице ConnectionLog — не выдержит),
   online-счётчики в Redis, реплики, событийная шина.

======================================================================

РЕШЕНИЯ, КОТОРЫЕ НУЖНЫ ОТ ТЕБЯ

======================================================================

Вопрос 1. Provisioning Module — утверждение модели.

Предложение Arena AI:

  model Device {
    id, userId, name, platform?, lastSeenAt?, createdAt, revokedAt?
  }

  model AccessKey {
    id, userId, deviceId?, name, protocol (VLESS по умолчанию),
    uuid (секрет, показывается один раз), serverId?, status
    (ACTIVE/REVOKED/EXPIRED), createdAt, expiresAt?, lastUsedAt?
  }

  Endpoints: POST/GET /provisioning/keys, PATCH /:id, POST /:id/revoke,
  POST /:id/rotate, GET /provisioning/config/:keyId (vless://-строка),
  CRUD /devices.

Требуется: утвердить / изменить / отклонить модель и эндпоинты.

Вопрос 2. Роли и entitlements.

Предложение: role ∈ {USER, ADMIN}; премиум-доступ — производное от
активной Subscription (entitlements: лимит устройств). PREMIUM-роль
оставить в enum для обратной совместимости, но не присваивать.

Требуется: утвердить отказ от role=PREMIUM (с планом миграции
существующих аккаунтов) или предложить альтернативу.

Вопрос 3. Протоколы.

Предложение: VLESS-first (один протокол платформы, экосистема Xray),
WireGuard — опционально позже. Официальное приложение подключается
через VLESS-движок (sing-box/xray-core) — существующий интерфейс
TunnelManager сохраняется как точка интеграции.

Требуется: утвердить единый протокол или dual-protocol.

Вопрос 4. Порядок фаз (Roadmap).

Предложение Arena AI:

  Phase A (нед. 1): Backend — Device/AccessKey, provisioning+devices
  модули, entitlements, deviceId в ConnectionLog.
  Phase B (нед. 2): Клиент — регистрация устройства, экраны
  Devices/Keys, QR (qr_flutter), импорт (share_plus), ProvisioningRepository.
  Phase C (нед. 3): Монетизация — POST /subscriptions/purchase +
  store webhook (замена локальной симуляции), refresh token, login UI.
  Phase D (по росту): Redis, PgBouncer, pre-aggregation, S3, события.

  Плюс product-позиция: продавать ключи + QR уже сейчас (любой VLESS-
  клиент), не дожидаясь официального приложения.

Требуется: утвердить порядок / изменить приоритеты.

Вопрос 5. Security ключей.

Предложение: UUID показывается один раз (экран+QR); мгновенный revoke
и rotate; шифрование ключей на уровне приложения (или pgcrypto);
аудит выдачи/отзыва.

Требуется: утвердить политику хранения ключей.

Вопрос 6. Аналитика.

Предложение: перейти на событийную модель (POST /analytics/events) +
hourly-rollups; не строить отчётность на данных до реального туннеля.

Требуется: утвердить событийный контракт (список событий) или
отложить.
