## 0. TL;DR

1. **Новость бьёт не по нам.** Запрет — это обязанность *российских* провайдеров
   хостинга проверять клиентов по реестру Роскомнадзора и отказывать на год.
   Физическая инфраструктура MOROK находится в ЕС (Хельсинки / Hostkey B.V. и
   Snowd Security OU), ни один узел не стоит в РФ.
2. **Один риск всё-таки есть:** сам аккаунт арендатора ведётся через российское юрлицо
   ООО «Админвпс» (adminvps.ru). Это посредник — он может потребовать
   верификацию через Госуслуги, сам отказать или получить жалобу от апстрима.
3. **Реальный риск для бизнеса не хостинг, а деньги и публичная реклама** —
   они в российской юрисдикции уже сейчас и уже сейчас под действующими нормами
   (ч. 18 ст. 14.3 КоАП, популяризация средств обхода).
4. **Что делаем:** переезжаем с российского посредника, разносим API-хост и
   VPN-ноду, убираем из публичных текстов лексику «обход блокировок»,
   смещаем приём денег в USDT/Stars.
5. **Отдельно, блокер релиза:** живая запись сервера в БД до сих пор отдаёт
   клиентам `sni=dl.google.com` (seed.ts её не чинит, потому что upsert идёт по
   другому IP). Фикс написан и проверен — `backend/prisma/fix-live-server.sql`.
   Заодно убраны опасные дефолты ключей в `xray-ingress.config.ts` (см. § 7).

| **Уже действует** | запрет популяризации средств обхода блокировок (ч. 10.8 ст. 5 38-ФЗ + ст. 13.41 КоАП) — работает независимо от слова «реклама» | с 01.03.2024 |

Важные оговорки, которые тонкие места делают важными:

* Норма **не** звучит как «поставил прокси — получил бан». Нужна связка:
  ресурс обеспечивает доступ к заблокированному **И** владелец не исполнил
  требование ст. 15.8. Для VPN-сервиса, построенного на доступе к
  заблокированному, «исполнить требование» практически нечем — то есть для
  MOROK попадание в реестр при российской площадке было бы почти неизбежным.
* Ограничение касается **провайдера хостинга, работающего в РФ**. Иностранный
  хостер под него не попадает — у него нет обязанности сверять с реестром.
* Регистрация на «российских хостингах через Госуслуги» в новостях —
  упрощение. В проекте обязанность идентификации лежит на хостере; как именно
  он её делает (Госуслуги/ЕСИА) — детали подзаконных актов.

## 3. План де-«роизации» инфраструктуры (30–90 дней, без простоя)

**Шаг 1 — уйти от российского посредника.**
Новый VPS напрямую у апстрима (Hostkey B.V., Hetzner, OVH, Contabo, AEZA и т.п.),
оплата картой/криптой, аккаунт не на РФ-юрлицо, e-mail не на mail.ru/yandex.
Старый сервер — источник, но **аккаунт-посредник — нет**.

**Шаг 2 — разделить роли хостов** (сейчас всё в одном месте, и это плюс к DPI-риску,
плюс к юридическому следу):

```
api.morokvpn.com     -> nginx + валидный Let's Encrypt, backend на 127.0.0.1:3000
node-1.morokvpn.com  -> Reality-нода, только 443; сертификат = decoy (*.telegram.org)
www.morokvpn.com     -> не светить как «сервер VPN»; либо заглушка, либо статика
```

В `toXrayIngressConfig()` (`backend/src/provisioning/xray-ingress.config.ts`) хост
берётся из `VpnServer.ip`, фолбэк — `morokvpn.com`. После разделения фолбэк должен
указывать на `node-1.morokvpn.com`, а `API_BASE_URL` в приложении — на
`https://api.morokvpn.com/app-api`.

**Шаг 3 — HTTPS для API уже пора.** Сейчас приложение ходит на
`http://...:3000/app-api` — URL, ключи и deviceId летят открытым текстом. Это
отдельная проблема релиза, не связанная с законом.

**Шаг 4 — чек-лист «нет российского следа»:**
- [ ] ни одного VPS/CDN в РФ (проверять `ip-api` по всем IP, включая будущие);
- [ ] нет `.ru` / `.рф` домена и нет российского регистратора;
- [ ] no Russian CDN (наш случай: не используем), no Яндекс.Метрика / VK Pixel /
      Mail.ru top@mail — любая аналитика из РФ сливает нас тем же органам;
- [ ] whois закрыт (WHOIS privacy), платёж за домен — не рублёвой картой;
- [ ] бэкапы — тоже вне РФ.

## 7. Патч живой БД (готов, проверен)

Причина: `prisma/seed.ts` делает `upsert` по `ip = '72.35.246.168'`, а рабочий узел
в БД лежит под `ip = 'morokvpn.com'` (`7491a3ee-f0c5-4f02-b3bb-563f54b2e5f1`).
Значит seed живую строку не трогает, и API до сих пор отдаёт:

```
{"id":"7491a3ee-…","ip":"morokvpn.com","sni":"dl.google.com","flow":"xtls-rprx-vision"}
```

`sni=dl.google.com` → `x509: certificate is valid for *.telegram.org, not dl.google.com`
→ соединение в sing-box/Hiddify отваливается по таймауту.

Дополнительно (TASK #028) в `xray-ingress.config.ts` дефолты sni/flow теперь
применяются **только** к `security=reality` — раньше они приклеивались и к
обычному VLESS-TCP, что ломало простые инбаунды. Ключевой материал (`pbk`/`sid`)
из кода больше не подставляется: узел без public key даёт
`INGRESS_CONFIG_INVALID` вместо «тихо неработающей» подписки. Проверено:
`npx jest` → 9 suites / 109 tests passed, `npx tsc --noEmit` → чисто.

Файл: `backend/prisma/fix-live-server.sql`
Скрипт: `npm run prisma:fix-server` (в `backend/`)

Прод крутится в docker-compose (`morok_postgres`, база `morok_vpn`, пользователь
`morok`), на хосте psql нет — поэтому на VPS:

```bash
cd /root/nexa_vpn/backend && git pull
docker compose exec -T postgres psql -U morok -d morok_vpn \
  -v ON_ERROR_STOP=1 -f - < prisma/fix-live-server.sql
curl -s http://morokvpn.com:3000/app-api/servers   # ждём "sni":"telegram.org"
```

Каталог, где лежит `docker-compose.yml`, если не угадал:
`sudo find / -name docker-compose.yml -not -path "*/node_modules/*" 2>/dev/null`.

Ожидаемый результат после применения (проверено на реальной схеме):

```
 id                                     | name              | ip           | port | security | sni          | flow               | status
 7491a3ee-f0c5-4f02-b3bb-563f54b2e5f1   | MOROK Fast FI-01  | morokvpn.com | 443  | reality  | telegram.org | xtls-rprx-vision   | ACTIVE
 aaaa1111-…   (дубль из seed)           | MOROK Fast NL-01  | 72.35.246.168| 443  | reality  | telegram.org | xtls-rprx-vision   | MAINTENANCE
```

Имя узла в фиксе — «MOROK Fast FI-01 / Helsinki», потому что 206.245.129.141
физически в Финляндии. Врём клиенту меньше — и в UI, и в логах будет правда.

## 8. Инцидент 01.10.2026: письмо АдминВПС про недоступность IP

Поддержка (тикет, администратор Д. Орел) сообщает: к отдельным IP «ограничения
доступа в сетях некоторых российских операторов» и предлагает 4 варианта —
замена IP за 199 ₽, подбор рабочего IP за 699 ₽, пересоздание услуги (данные
удаляются), миграция в другую локацию (простой до 1 часа).

Что это значит технически: TCP-порты 22/80/443/3000/8000 на `206.245.129.141`
из этой среды (ЕС) открыты, `/app-api/health` отвечает `{"status":"ok"}`. То есть
сервер жив, а речь о проблемах досягаемости именно из российских сетей — либо
частичный DPI-блокинг по IP, либо деградация маршрута. Это отдельный класс
проблемы: не «закон» и не «наш конфиг», а маршрутизация до нашего IP.

Приоритет решений:

| Вариант | Оценка |
|---|---|
| Подбор рабочего IP за 699 ₽ | **не берём.** Купка одного IP, пока вся система стоит на одном IP; завтра он же станет недоступен |
| Замена IP за 199 ₽ | **не берём.** Тот же пул, «гарантий нет», + теперь и платный, и сломанный по SNI сервис |
| Пересоздание услуги (бесплатно) в другой локации | **наш выбор №1**, если миграция мешает: чистый IP + чистый контур, всё поднимается за 15 минут через `deploy/bootstrap.sh` |
| Миграция в другую локацию (бесплатно, до 1 ч простоя) | **наш выбор №2**, если хочется сохранить узел/ключи Marzban как есть |

Ответ в тикет должен содержать: (а) только не-РФ локации, (б) два вопроса — про
исключение адресов из реестра блокируемых и про альтернативные подсети, (в)
уточнение, что «нет гарантий» принимается и дальнейшую устойчивость мы решаем
архитектурно (2–3 узла, домен вместо IP, отдельный API-хост), а не покупкой IP.

Архитектурный вывод из инцидента (важнее, чем сами 199/699 ₽): **единственный
IP = единая точка отказа**. После переезда обязательно: узел описан доменом
(уже так), A-запись = вся адаптация к смене IP; второй узел = второй провайдер;
API отдельно на `api.<домен>` с HTTPS. См. `deploy/README.md`.

Порядок действий при пересоздании/миграции — в `deploy/README.md`. Ключевое:
`fix-live-server.sql` + пересборка APK применяются **независимо** от того, какой
IP даст АдминВПС; иначе платим за IP и получаем ровно тот же неработающий VPN.
