# Ядро узла: выдача ключей → клиенты в Xray (TASK #030)

## Что было сломано

`AccessKey.uuid` — это обещание, а не пропуск. Пускает ядро, и пускает оно только
тех, кто лежит в `inbounds[].settings.clients`. На проде список был пуст (0 клиентов
при 2 активных ключах), поэтому клиент получал валидный `vless://…`, импортировал его
и ловил ошибку TLS-handshake. Никакого «неверного ключа» в логах приложения при этом
нет — ошибка рождается на узле.

Второй слой проблемы: панель Marzban держит ядро как `xray run -config stdin:` и
генерирует конфиг сама. Правка `/var/lib/marzban/xray_config.json` + SIGHUP до такого
процесса не доходит — проверено живьём (3 клиента в файле, `processed invalid connection`
у клиента, даже после `docker restart`).

## Как устроено сейчас

```
backend  XrayClientSyncService ──пишет──> /var/lib/morok/xray-clients.json   (том с хостом)
                                          │  (+ интервал 30 с, + сразу после redeem/issue/revoke)
cron     build-xray-config.py <───────────┘
            │ reality-ключи: /var/lib/morok/reality-keys.json
            ▼
        /etc/morok/xray/config.json  ──> systemd morok-xray.service (порт 443)
```

Marzban-контейнер выключен (`--restart=no`), его данные и конфиг не тронуты —
там остались БД панели и сертификаты, при желании панель возвращается.

## Установка на узле

```
cd /opt/morok_app && git pull && bash deploy/xray-sync/install-node.sh
```

`install-node.sh` идемпотентен: скачивает xray (если нет), забирает Reality-ключи из
конфига панели (URI пользователей не меняются), пишет юнит, отбирает :443 у Marzban,
ставит cron. `SKIP_SWAP=1 bash deploy/xray-sync/install-node.sh` — прогон без отбора
порта (для проверки).

## Проверка

```
python3 deploy/xray-sync/probe-node.py            # на узле: наше ядро против ядра панели
tail -5 /var/log/morok-xray-sync.log
```

Панель: `GET /app-api/provisioning/xray/status` → `desired` (активных ключей в базе),
`published` (выложено файлу), `nodeClients` (ядро применило). Все три равны — узел пускает.

Живая проверка туннеля с любой машины: подняв xray-клиент с URI из `/provisioning/:id`,
убедиться, что внешний адрес сменился на адрес узла.

## Что решено осознанно

* **Перезапуск вместо hot-reload.** Xray не перечитывает конфиг по SIGHUP (сигнал
  означает остановку), поэтому применение конфига = `systemctl restart` ≈ 1 с, активный
  туннель за это время падает и переподнимается сам. Чтобы не рвать соединения почём
  зря, конфиг переписывается только при реальном изменении списка клиентов (хэш).
  Правильное решение на вырост — xray API (`stats`/`handler` + gRPC `AddClient`),
  оно даёт мгновенную выдачу без рестарта; требует включённого api-модуля в конфиге.
* **В ядро попадают все ACTIVE-ключи**, в т.ч. ещё не активированные. Отказ в доступе
  решается на уровне выдачи конфига (`toContract`), а не ACL ядра: лишняя запись в
  clients без рабочего клиента не даёт доступа никому, зато отзыв ключа обязан
  доходить до ядра — за это отвечает тот же sync.
* **access-лог ядра выключен** (`log.loglevel: warning`, без `access`): бэкенд уже не
  хранит ни логов подключений, ни привязку «кто куда ходил» — см. docs/RISK_ASSESSMENT_RF.md.
